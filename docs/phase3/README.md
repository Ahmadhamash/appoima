# JorMall — Phase 3 scheduling implementation candidate

Internal staff application for beauty and wellness clinics. The binding specification is `JORMALL_REPLIT_SPEC.md`; the continuation requirements are in `CODEX_PROMPT_PHASES_2-5.md`.

**Scheduling is implemented in source. This is not a verified release.** The user authorized Phase 3 after the Phase 2 delivery. Phase 2 acceptance gaps remain open; full workspace typechecking, real PostgreSQL/API tests, migrations, builds, and browser acceptance could not run here. **Phase 4 waiting list/inventory and Phase 5 assistant were not started.**

## What is included

Phase 1 owner/clinic creation, authentication, forced password change and server-defined navigation remain. Phase 2 branches/hours, services, rooms, staff access/schedules, customers and sensitive-note protections remain.

Phase 3 adds:

- **Booking:** Customer (search or add inline) → Service/branch → Employee → Available date/time → Review → Book. Availability is fetched from the API; a required compatible room is selected and reserved by the server. There is one Create appointment entry per page, not competing creation controls.
- **Appointments:** daily view, month calendar with actual aggregated counts, paginated full history, filters, appointment detail and rescheduling. Branch-local display, UTC storage.
- **Lifecycle:** Pending → Confirmed → Checked in → In service → Completed, plus allowed cancellation/no-show transitions. The API supplies valid next actions. Cancellation and rescheduling require a reason and confirmation; rescheduling preserves the history and resets confirmation.
- **Role homes:** secretary/manager today's appointments; doctor/provider own appointments and next customer. Assigned providers can start/finish and record operational notes without global appointment-management permission.
- **Real data integration:** customer appointment history and manager checklist first-booking completion.
- **Database safeguards:** employee/room exclusion constraints, tenant-composite foreign keys, transactional availability recheck, version checks, durable idempotency records, history and audit writes in the same transaction.

Every new UI message has EN/AR copy. Entered names and appointment notes preserve their selected language. Stored names are never translated. Restricted customer notes are excluded from unauthorized responses, not merely hidden with CSS. Logout now removes all private setup/customer/scheduling caches rather than retaining everything under the old `setup` query prefix.

## Runtime and installation

Use the repository's Node 24/Replit runtime and existing pnpm lockfile. No new application dependencies were added. Set secrets in the environment, not source files:

```text
DATABASE_URL=postgresql://<user>:<password>@<host>:5432/<database>
SESSION_SECRET=<long-random-secret>
```

Scripts do not automatically read a root `.env` file. Configure database transport security for the target host. Install:

```bash
pnpm install --frozen-lockfile
```

## Database — choose the correct path

Back up before changes. Run acceptance against a disposable database, never real clinic/customer data. Full details and migration limitations: `lib/db/migrations/README.md`.

**Fresh empty database:**

```bash
pnpm --filter @workspace/db run migrate
```

This applies the Phase 1 baseline, Phase 2 setup, and `0002_phase3_scheduling.sql`. The SQL files are hand-authored; they were not generated by Drizzle or executed here. Review and test them before deployment.

**Existing database with Phase 1 and Phase 2 already recorded in Drizzle's migration journal:** back up, review the new SQL, then run the same `migrate` command. Only the new Phase 3 migration should apply. Verify the journal before assuming this.

**Existing push-managed Phase 2 database:** use the development push wrapper only on a reviewed development copy, or have its schema/journal reconciled before adopting versioned migrations. Do not run the fresh baseline on existing tables. The old `adopt-phase1` script is ONLY for an unchanged Phase 1 layout; it intentionally refuses Phase 2 tables.

**Disposable development database using the requested push workflow:**

```bash
pnpm --filter @workspace/db run push
```

The wrapper runs `drizzle-kit push` and then installs the custom SQL overlap guards. Do not bypass it with bare `drizzle-kit push`, and do not use `push-force` to suppress warnings. Push does not register versioned migration history. Reinstall guards explicitly after a reviewed schema repair:

```bash
pnpm --filter @workspace/db run install-scheduling-guards
```

The API refuses startup if the named exclusion constraints are missing or invalid. Creating `btree_gist` requires suitable database privileges. Installing constraints fails if existing appointments overlap; no script deletes or moves records to make the checks pass.

### Drizzle snapshots

pnpm --filter @workspace/db run prepare-snapshots
# After metadata is reviewed, for a deliberate later schema change:

## Run and seed

After the database is ready, restart both workflows in separate terminals:

```bash
pnpm --filter @workspace/api-server run dev
pnpm --filter @workspace/jormall run dev
```

API: port 5000 under `/api`; web: port 19880, base `/` by default. Outside Replit, Vite proxies `/api` to port 5000. Existing Replit routing is preserved.

Initial setup remains: platform owner → clinic and manager account → manager signs in and replaces the initial password. The new scheduling API will not bypass forced password changes.

```bash
pnpm --filter @workspace/api-server run seed
```

Development seed preserves existing sample passwords/access and fills the two sample clinics with setup data. It now attempts one real future pending appointment per sample clinic without an existing appointment, using real schedules/rooms/availability and transactional history. No available slot within 14 days means no fabricated booking. New sample passwords are random and printed only once; every new user must change theirs. An absent owner requires explicit `SEED_OWNER_EMAIL` / `SEED_OWNER_PASSWORD`. Do not retain credential output in shared logs.

## Permissions and operating decisions

Doctors/providers have implicit assigned-only appointment access. **New** role presets do not grant global appointment read/manage. Existing saved permission arrays are intentionally unchanged: review existing provider accounts to remove old global grants when assigned-only access is intended. Explicit `appointments.read` or `appointments.manage` allows viewing other employees' appointments; manage also permits scheduling. Providers' home screens still default to their own work.

General appointment-read access does not reveal operational appointment notes. These are available to authorized appointment managers and the assigned provider. Customer contact/general notes require `customers.read`; sensitive customer notes require `customers.manage`. Reads of sensitive notes are audited. A detail read holds the same clinic advisory lock as reassignment/setup while permissions and sensitive data are checked.

Slot starts use a 15-minute grid. Service duration need not be a multiple of 15. Hours/breaks are same-day ranges, as in Phase 2; overnight ranges and `24:00` closing are not supported. DST gaps/folds and appointments stretched by a DST transition are omitted conservatively. All non-cancelled statuses retain their historical reservation, including completed/no-show, as requested. Room capacity is descriptive, not permission for overlapping bookings. Rescheduling retains booked duration/room requirement rather than rewriting old appointments from later service edits.

Availability and mutations coordinate with setup through a clinic-level advisory lock. This prioritizes correctness over maximum write throughput; no load/capacity claim has been validated. PostgreSQL exclusions are the final overlap backstop, including independent inserts that skip application prechecks.
