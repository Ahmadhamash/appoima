# Codex Cloud and deployment

Repository: `Ahmadhamash/appoima`. Codex Cloud checks out the selected GitHub branch. Choose this repository and the branch containing the latest commit in the Codex task screen. The [official Codex Cloud guide](https://learn.chatgpt.com/docs/cloud) explains environment creation and branch selection. A local uncommitted file is not present in a cloud task.

The workflow in `.github/workflows/ci-deploy.yml` runs typecheck, database-independent tests, and production builds on each PR and `main` push. Its deployment job runs after CI on a production runner and applies the versioned migrations, restarts `jormall-clinic.service`, and verifies `/api/healthz`. It is disabled until the repository variable `DEPLOY_ENABLED` is set to `true`.

The production server currently uses `/opt/jormall-clinic` and `/etc/jormall-clinic.env`. Its `100.61.125.129` address belongs to a private network, so a GitHub-hosted runner cannot reach it directly. The repository is currently public. **Make it private before installing a self-hosted runner or enabling deployment**; GitHub [recommends self-hosted runners only for private repositories](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners). The workflow also requires the repository to be private before its deployment job can start. Install a repository-level self-hosted Linux x64 runner on the server with the extra label `jormall-production` using GitHub **Settings → Actions → Runners → New self-hosted runner**. Run it as a dedicated unprivileged account. Give that account write access to `/opt/jormall-clinic` and read access to `/etc/jormall-clinic.env`, plus passwordless `sudo systemctl status/stop/restart jormall-clinic.service`. Keep the runner's own directory outside `/opt/jormall-clinic` and protect `main`.

Before enabling deployment, install Node 22, pnpm 10, `rsync`, PostgreSQL client tools (`pg_dump`), and `curl` on the server. Verify that the existing database's Drizzle migration journal matches the repository's SQL migrations 0000–0015 on a database copy. A populated or push-managed database may need reconciliation; the workflow never uses `push-force`. The deployment script creates a database dump, saves the previous API and web bundles, and restores those bundles if restart or health check fails. Database changes are additive and are not automatically reversed.

Create a GitHub Environment named `production`, protect it as appropriate, and set the repository variable `DEPLOY_ENABLED=true` only after the runner and migration rehearsal are ready. A push to `main` then deploys automatically. The workflow's `Deploy to clinic server` job and the endpoint `https://100-61-125-129.sslip.io/` provide the release checks. Server secrets remain in `/etc/jormall-clinic.env`; never add them as repository files.
